# v1.1 small-file speed: first round (2026-11-14)

Branch `v1.1-small-files`, not pushed and not released. Test: 20,000 files of 1–64 KB (632 MB), C:→C: (Crucial MX500),
HyperCopy CLI `--conflict overwrite` vs `robocopy /E /MT:16 /NFL /NDL /NJH /NJS /NP`, destination wiped before every
run, tool order alternated each round. No flush for either tool (same as `tools/benchmark.ps1`).

**The PC was noisy.** Every tool, Robocopy included, varied by up to 2× between runs (Robocopy 6.7–14.6 s), and
everything was slower than the v1.0 numbers (10.6 s vs 5 s). Medians are below. Compare the tools within one
round, not across rounds.

## What I changed
**Small files keep their creation time without a second open of the new file.** Until now each small file
needed `File.Copy` (CopyFileEx) and then `File.SetCreationTimeUtc`, which opens the new file again, sets the
time and closes it. Now HyperCopy calls CopyFileEx itself with a progress callback. When the data stream starts,
the callback sets the creation time through CopyFileEx's own destination handle (`SmallFileCopy.cs`). If the
callback didn't stamp it, the old by-path method still runs as a fallback. Robocopy keeps creation time as well
(checked), so dropping it was not an option.

## Results (seconds, median; the individual runs are in brackets)
| Round | Current code (v1.0.2) | New code | Robocopy /MT:16 |
|---|---|---|---|
| Profiling, 3 runs | 19.2 (25.2, 19.2, 14.7) | 16.4 (16.4, 17.6, 12.3) | 9.2 (9.8, 9.2, 8.2) |
| Profiling, 5 runs | 18.3 (15.1, 18.3, 16.5, 21.1, 24.4) | 15.6 (13.1, 14.4, 15.6, 19.1, 18.8) | 10.8 (9.8, 8.1, 11.6, 11.3, 10.8) |
| Final build, 5 runs | 25.7 (17.0, 32.1, 26.0, 25.7, 22.9) | 21.1 (14.7, 21.1, 28.6, 19.9, 24.8) | 11.6 (6.7, 7.7, 11.6, 14.6, 12.6) |

In every round the new code's median is about **15% lower** than the current code's. In the side-by-side pairs
it won 5/5, 3/3 and 3/5. **HyperCopy is still about 1.7–1.8× slower than Robocopy.** This change narrows the
gap a little and does not close it. With noise this large, the 15% is probable, not proven.

## What else I measured (test-only switches, not kept)
| Experiment | Median | Verdict |
|---|---|---|
| Skip the creation-time restore entirely | 16.5 s (vs 19.2) | This is where the 15% comes from. The callback wins it back while keeping the feature. |
| Skip the "does the destination exist?" check | 20.5 s (vs 19.2) | No gain. Kept. |
| Skip both (bare CopyFileEx, nothing else) | 16.9 s (vs Robocopy 10.8) | **Most of the gap is inside CopyFileEx itself**, not in HyperCopy's own per-file work. |
| Scan time / start-up | 0.14 s / 0.15 s | Not a factor. |

Ideas from the roadmap that turned out not to apply:
- *Batched directory creation:* already done. The engine creates all folders up front, before any file is copied.
  Only the same-drive "move by rename" path creates folders per file, and that path is instant anyway.
- *Attribute setting:* already skipped when the attributes are plain "Archive" (the normal case).

## Tests
`dotnet test -c Release`: **44 passed** (38 existing + 6 new):
- `Small_copy_stamps_creation_time_through_copy_handle` (0 B, 1 B, 4 KB, 300 KB; read-only + hidden source):
  creation and modified time, attributes, content, and that the callback really did the stamping.
- `Small_copy_reports_errors_like_File_Copy`: missing file, "already exists", sharing violation (code 32, so the
  locked-file fallback still triggers), and disk full (code 112 stays an `IOException`). This test caught a real bug
  in the first draft: .NET's `Marshal.GetExceptionForHR` returns a `COMException` for some codes, which would have
  broken disk-full detection.
- `Small_files_overwrite_readonly_destination_and_keep_times`: 50 files, one overwriting a read-only file, verify on.

## Not tested
- HDD, USB sticks, exFAT/FAT32 and network destinations with the new path. These use the same CopyFileEx call, but no
  timing or behaviour was measured. A FAT32 destination has no creation-time support problem here, since the stamp is
  best-effort and falls back to the old method.
- App start-up time: not re-measured, because only the engine changed (no app, build or compression settings).

## Recommended next step
The remaining ~1.7× gap is inside CopyFileEx, so more small tweaks in HyperCopy won't close it. Next:
1. Re-measure on a quiet PC: after a reboot, with Windows Search indexing paused, 5+ runs. This confirms the 15%
   before merging.
2. Record one Robocopy run and one HyperCopy run with Windows Performance Recorder (`wpr -start FileIO`) or Process
   Monitor, and compare the calls made per file. Robocopy may avoid CopyFileEx (for example its own open/read/write
   with different sharing or caching flags) or skip extra stream and security queries. That tells us what to copy
   from it.
3. If Robocopy turns out to use plain handle copies with special flags, retest handle-based copying with exactly
   those flags. The v1.0 handle-based test was 4–8× slower, but it used different flags.
